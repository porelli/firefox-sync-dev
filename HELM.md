# Kubernetes with Helm

The Helm chart [charts/firefox-sync](/charts/firefox-sync) runs the Sync server of [SYNC.md](SYNC.md) on Kubernetes: syncstorage-rs with its tokenserver, its migrations and the init container of `maxUsers`, the databases (MariaDB, MySQL 8.4 or PostgreSQL, or [your own server](DATABASES.md#kubernetes)), and optionally the [admin UI](ADMIN.md) and the nightly backups. The same images as docker compose and the Quadlets, the same settings under the names of the chart's values.

Not in the chart yet: the self-hosted Mozilla accounts ([FXA.md](FXA.md)). Firefox signs in with Mozilla's accounts; for your own accounts use docker compose or the Quadlets.

## What you need

- Kubernetes 1.27 or later (the backups' CronJob runs in UTC with `timeZone`), and Helm 3
- A default StorageClass, or `database.persistence.storageClass` (and `backup.persistence.storageClass`): one volume per database server, one for the backups
- A host name with HTTPS that reaches the Sync server: an Ingress controller (`ingress.enabled`, below), or your own reverse proxy in front of the Service `<release>-firefox-sync-syncstorage`, port 8000

## Install

The chart is published as an OCI artifact next to the images:

```bash
helm install ffs oci://ghcr.io/porelli/firefox-sync/charts/firefox-sync --version 0.1.0 \
  -f my-values.yaml --wait --timeout 10m
```

`ffs` is the release name: the objects are called `ffs-firefox-sync-*`, which the commands below use. Add `-n <namespace> --create-namespace` for a namespace of its own (and `-n <namespace>` to every `kubectl` command). A minimal `my-values.yaml`, with ingress-nginx and cert-manager:

```yaml
syncDomain: https://sync.example.com
# how many accounts can use the server, as SYNC_MAX_USERS (SYNC.md#who-can-use-your-server)
maxUsers: "5"
ingress:
  enabled: true
  className: nginx
  tls:
    enabled: true
    secretName: sync-example-com-tls
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    # Firefox uploads up to about 2 MB per request: nginx's default is 1 MB
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
```

`helm install` prints what to do next (the NOTES). The first start takes a minute or two: the databases are created, then the migrations and the init container run before the Sync server. Then set up Firefox as in [SYNC.md](SYNC.md#firefox-setup), with `https://sync.example.com/1.0/sync/1.5`.

```bash
kubectl get pods -l app.kubernetes.io/instance=ffs
kubectl logs deploy/ffs-firefox-sync-syncstorage -c db-init   # Current users: N
```

The settings, as in `.env`:

| Values | `.env` | Default |
|---|---|---|
| `syncDomain` | `SYNC_PUBLIC_URL` | required |
| `maxUsers` | `SYNC_MAX_USERS` | `"1"` (`initial:N` lets the admin UI manage it) |
| `database.backend` | `SYNC_DB` (and the PostgreSQL compose file) | `mariadb`; `mysql` (8.4) or `postgres` |
| `database.bundled` | `SYNC_DB_CONTAINERS` | `true`; `false`: [your own server](DATABASES.md#kubernetes) |
| `database.image.postgres` | `SYNC_POSTGRES_IMAGE` | `postgres:18` |
| `database.image.mariadb`, `.mysql` | none (compose has them fixed) | `mariadb:lts`, `mysql:8.4` |
| `fxa.oauthServerUrl`, `fxa.emailDomain` | `FXA_OAUTH_SERVER_URL`, `FXA_EMAIL_DOMAIN` | Mozilla's accounts |
| `image.repository`, `image.syncstorageTag`, `image.initTag`, `image.adminTag` | `IMAGE_REPOSITORY`, `SYNC_IMAGE_TAG`, `SYNC_INIT_IMAGE_TAG`, the tag of `ADMIN_IMAGE` | `ghcr.io/porelli/firefox-sync`, `latest` |
| `admin.*` | `ADMIN_*`, `FXA_SMTP_*` | the admin UI off |
| `backup.*` | `COMPOSE_PROFILES=backup`, `BACKUP_KEEP` | the backups off |
| `existingSecret` | the passwords and secrets of `.env` | a Secret generated by the chart |

Every value is in [values.yaml](/charts/firefox-sync/values.yaml), with what it does (`nameOverride` and `fullnameOverride` too).

## The Secret

The chart generates the secrets of `.env` on the first install into the Secret `ffs-firefox-sync` and reads them back on every `helm upgrade` (Helm's `lookup`): `SYNC_MASTER_SECRET`, `METRICS_HASH_SECRET` (`.env`'s `SYNC_METRICS_HASH_SECRET`), `ADMIN_PASSWORD` (unless you set `admin.password`) and the database passwords never change. A key that a new chart version adds is generated at the upgrade. The Secret has `helm.sh/resource-policy: keep`: `helm uninstall` leaves it, like the databases' volumes, so that a new install with the same release name finds the passwords the databases were created with.

Keep a copy of it, with your values, off the cluster: the backups do not have it.

```bash
kubectl get secret ffs-firefox-sync -o json \
  | jq '{apiVersion, kind, type, data, metadata: (.metadata | {name, labels, annotations})}' > ffs-secret.json
```

The optional secrets of the admin UI are the values' alone: `admin.smtp.password`, `admin.oidc.clientSecret`, `admin.metricsToken` and `admin.notify` are written into the Secret on every install and upgrade (`FXA_SMTP_PASS`, `ADMIN_OIDC_CLIENT_SECRET`, `ADMIN_METRICS_TOKEN`, `ADMIN_NOTIFY`), and an empty value turns that feature off, whatever was put into the Secret by hand.

### existingSecret

A Secret of your own, which the chart reads and never writes. Required:

- with your own database server (`database.bundled: false`): the chart cannot generate passwords your server knows;
- when the chart is rendered without the cluster: `helm template`, or a GitOps tool that renders it (Argo CD...). `lookup` finds nothing there, and every render would generate new secrets: every Firefox signed out, the databases refusing the new passwords.

Its keys:

| Key | Backend | |
|---|---|---|
| `SYNC_MASTER_SECRET` | all | the Sync server's tokens (`.env`: `SYNC_MASTER_SECRET`) |
| `METRICS_HASH_SECRET` | all | the hash of the account ids in the metrics (`.env`: `SYNC_METRICS_HASH_SECRET`) |
| `ADMIN_DB_PASSWORD` | all, but MariaDB and MySQL on your own server without the admin UI and the backups | the admin UI's two database users ([DATABASES.md](DATABASES.md#the-admin-uis-own-database)): the bundled MariaDB and MySQL create them, the PostgreSQL init container creates them, the admin UI and the backups log in with it |
| `TOKENSERVER_DB_PASSWORD`, `STORAGE_DB_PASSWORD` | `mariadb`, `mysql` | the tokenserver and storage users |
| `POSTGRES_PASSWORD` | `postgres` | the superuser of the bundled server; on your own server the owner, `database.external.postgresUser` |
| `POSTGRES_SYNC_PASSWORD` | `postgres`, bundled | the Sync server's own role `syncserver_app` (`database.postgresSyncUser`), no superuser |
| `ADMIN_PASSWORD` | optional | the admin UI's password; missing or empty: no password form (sign in with OpenID Connect or a header, [ADMIN.md](ADMIN.md#signing-in)) |
| `FXA_SMTP_PASS`, `ADMIN_OIDC_CLIENT_SECRET`, `ADMIN_METRICS_TOKEN`, `ADMIN_NOTIFY` | optional | the admin UI's; missing or empty: that feature off. With `existingSecret` the values of `admin.password`, `admin.smtp.password`, `admin.oidc.clientSecret`, `admin.metricsToken` and `admin.notify` are not read |

E.g. for MariaDB or MySQL:

```bash
rnd() { LC_ALL=C tr -dc A-Za-z0-9 < /dev/urandom | head -c 32; }
kubectl create secret generic ffs-secrets \
  --from-literal=SYNC_MASTER_SECRET="$(rnd)" --from-literal=METRICS_HASH_SECRET="$(rnd)" \
  --from-literal=ADMIN_PASSWORD="$(rnd)" --from-literal=ADMIN_DB_PASSWORD="$(rnd)" \
  --from-literal=TOKENSERVER_DB_PASSWORD="$(rnd)" --from-literal=STORAGE_DB_PASSWORD="$(rnd)"
```

and `existingSecret: ffs-secrets` in your values (with PostgreSQL `POSTGRES_PASSWORD` and `POSTGRES_SYNC_PASSWORD` instead of the last two). With a GitOps tool, the same keys from your secrets manager (Sealed Secrets, External Secrets...). A key missing that a pod needs stops it in `CreateContainerConfigError` (`kubectl describe pod` names the key) until it is there: a new chart version that needs a new key says so in its release notes. (`ADMIN_DB_PASSWORD` and `POSTGRES_SYNC_PASSWORD` were added during the development of 0.1.0, the first release: a Secret made for a pre-release before them lacks them.)

## Your own database server

`database.bundled: false`, `database.external.*` and an `existingSecret` with the passwords of the users you created: [DATABASES.md](DATABASES.md#kubernetes). With MariaDB or MySQL, `database.external.tlsVerify` is `false` by default (MySQL's own certificate is self-signed, a managed service's CA is not in the images); `true` needs a certificate from a CA the images trust, for that host name.

## Ingress

`ingress.enabled` publishes the Sync server at `/` of `ingress.host` (empty: the host of `syncDomain`), with the controller of `ingress.className`. `ingress.tls.enabled` with `ingress.tls.secretName` (empty: the controller's default certificate); cert-manager needs a `secretName` to write the certificate into. With ingress-nginx, raise `nginx.ingress.kubernetes.io/proxy-body-size` (`"10m"` above): Firefox sends batches up to the Sync server's limit, about 2 MB a request, and nginx refuses more than 1 MB by default (`413 Request Entity Too Large`, in `about:sync-log`). Other controllers: their own limit of the request body, if they have one.

Without it, publish the Service `ffs-firefox-sync-syncstorage:8000` your own way, at `syncDomain`.

The admin UI never shares that Ingress: see below.

## The admin UI

```yaml
admin:
  enabled: true
  alertEmail: you@example.com
  smtp:
    host: smtp.example.com
    user: sync@example.com
    password: <the SMTP password>
    sender: sync@example.com
```

The values are those of `.env` under other names: `admin.alertEmail` is `ADMIN_ALERT_EMAIL`, `admin.smtp.*` `FXA_SMTP_*`, `admin.oidc.*` `ADMIN_OIDC_*`, `admin.notify` `ADMIN_NOTIFY` (a list of URLs), `admin.tz` `ADMIN_TZ`, and so on, each one in [values.yaml](/charts/firefox-sync/values.yaml). Its pages then give the chart's commands (`kubectl`, `helm upgrade ... --reuse-values --set ...`) and the names of the values instead of `.env` and docker compose.

It is not published. Reach it with a port-forward and open `http://localhost:8090`:

```bash
kubectl port-forward svc/ffs-firefox-sync-admin 8090:8080
kubectl get secret ffs-firefox-sync -o jsonpath='{.data.ADMIN_PASSWORD}' | base64 -d   # the password
```

Or give it its own Ingress, on a host of its own (the chart refuses the Sync server's host), behind your own sign-in: the admin UI can delete accounts and change who signs up. E.g. only from your network, or with OpenID Connect ([ADMIN.md](ADMIN.md#signing-in), `admin.oidc.*`, with `admin.oidc.redirectUrl: https://admin.example.com/auth/callback`) or a forward-auth proxy (`admin.trustedHeader.*`):

```yaml
admin:
  enabled: true
  ingress:
    enabled: true
    className: nginx
    host: admin.example.com
    tls:
      enabled: true
      secretName: admin-example-com-tls
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
      nginx.ingress.kubernetes.io/whitelist-source-range: 192.0.2.0/24
```

Without `admin.ingress.tls.enabled` the NOTES warn: unless the controller adds TLS, the password and the session cookie cross the network in plain HTTP.

## Backups

```yaml
backup:
  enabled: true
  schedule: "0 3 * * *"   # cron, UTC
  keep: 7
```

The CronJob `ffs-firefox-sync-backup` runs the backup service of compose ([ADMIN.md](ADMIN.md#backups)) in the database's image: it dumps the tokenserver, the storage and the admin UI's database, as the stack's users, into the PersistentVolumeClaim `ffs-firefox-sync-backups`, `sync/<UTC time>/<database>.sql.gz`, and keeps the newest `keep` runs. Each run is on the admin UI's overview, with an alert when one fails or the last good one is older than 36 hours. The PVC is kept on `helm uninstall`.

- `schedule`: a daily `M H * * *` is also what the admin UI says ("every night at 03:00 UTC"). Any other schedule runs as given, but that text is then approximate; and one rarer than every 36 hours makes the alert of a too old backup fire between runs.
- `activeDeadlineSeconds` (82800, 23 hours): a run still going then is stopped and fails. One run at a time (`concurrencyPolicy: Forbid`): a hung dump would hold back every later one.
- With your own database server too (`database.bundled: false`), as the users of its SQL, next to the server's own backups.

One now, under a new Job name each time (the command of the admin UI's Backups card):

```bash
kubectl create job --from=cronjob/ffs-firefox-sync-backup backup-now-$(date +%s)
```

### Copy them off the cluster

The PVC is in the cluster, often on the same storage as the databases. Copy it elsewhere, e.g. every morning, with a pod that mounts it (the dumps are root's, 0600):

```bash
kubectl run ffs-backups --image=busybox --restart=Never --overrides='{"spec": {"containers": [{"name": "ffs-backups",
  "image": "busybox", "command": ["sleep", "3600"], "volumeMounts": [{"name": "backups", "mountPath": "/backups"}]}],
  "volumes": [{"name": "backups", "persistentVolumeClaim": {"claimName": "ffs-firefox-sync-backups"}}]}}'
kubectl wait --for=condition=Ready pod/ffs-backups
kubectl exec ffs-backups -- tar -C /backups -czf - . > ffs-backups.tar.gz
kubectl delete pod ffs-backups
```

The PVC is `ReadWriteOnce`: while a backup runs on another node the pod waits for it. Keep the copy as private as the Secret: the dumps hold the event log and the accounts' ids.

### Restoring

On the same cluster, or on a new one. On a new one first:

1. Create your copy of the Secret, in the same namespace: `kubectl apply -f ffs-secret.json` (`helm install` with the same release name takes it over, and keeps its data), or your `existingSecret`.
1. `helm install` with your values, as at the start, with `backup.enabled: true`: the restore runs in Jobs of the backup CronJob, on its PVC.
1. Put the copy of the backups back, with the pod of [Copy them off the cluster](#copy-them-off-the-cluster): `kubectl exec -i ffs-backups -- tar -C /backups -xzf - < ffs-backups.tar.gz`.

Then, as [ADMIN.md#restoring](ADMIN.md#restoring) says for compose (what to restore and in which order, why the storage is better left empty), with `F=ffs-firefox-sync`:

1. Stop the Sync server and the admin UI: `kubectl scale deploy/$F-syncstorage --replicas=0`, and `kubectl scale deploy/$F-admin --replicas=0` with the admin UI.
1. Empty databases: PostgreSQL's dump loads only into an empty database, so there always (the dumps of MariaDB and MySQL drop and create each table again, into the old databases too). The data of a database server is its PVC, `data-<its pod>`:

    ```bash
    for db in postgres; do   # MariaDB and MySQL: tokenserver-db storage-db
      kubectl scale sts/$F-$db --replicas=0
      kubectl wait --for=delete pod/$F-$db-0 --timeout=5m
      kubectl delete pvc data-$F-$db-0
      kubectl scale sts/$F-$db --replicas=1
      kubectl rollout status sts/$F-$db --timeout=30m
    done
    ```

1. A run: `run=20261013T030000Z`, one of the list of the pod of [Copy them off the cluster](#copy-them-off-the-cluster) (`kubectl exec ffs-backups -- ls /backups/sync`). Delete that pod before the restores (`kubectl delete pod ffs-backups`): the PVC is `ReadWriteOnce`, and on another node the Jobs below would wait for it. Each restore runs ADMIN.md's command in a Job of the backup CronJob's spec (its variables, its volume), as the stack's users:

    ```bash
    restore() {   # restore <job name> <command>
      kubectl create job --from=cronjob/$F-backup "$1" --dry-run=client -o json |
        jq --arg c "$2" '.spec.template.spec.containers[0] |= (.command = ["sh", "-c", $c] | del(.args))' |
        kubectl apply -f - || return 1
      local deadline=$(( $(date +%s) + 600 ))
      until kubectl get job "$1" -o jsonpath='{.status.conditions[*].type}' | grep -qE 'Complete|Failed'; do
        [ "$(date +%s)" -lt "$deadline" ] || { echo "job/$1 not done after 10 minutes: kubectl describe job/$1"; return 1; }
        sleep 2
      done
      kubectl logs "job/$1"
      [ "$(kubectl get job "$1" -o jsonpath='{.status.succeeded}')" = 1 ]
    }
    ```

1. MariaDB and MySQL (`mysql` instead of `mariadb` with MySQL): the tokenserver, then the admin UI's database (the database servers create it, empty, at their start); the storage only when no device has the data any more:

    ```bash
    restore restore-tokenserver 'f=/backups/sync/'$run'/$TOKENSERVER_DB_NAME.sql.gz
      gunzip -t "$f" && gunzip -c "$f" | mariadb -h "$TOKENSERVER_DB_HOST" -u"$TOKENSERVER_DB_USER" -p"$TOKENSERVER_DB_PASSWORD" "$TOKENSERVER_DB_NAME"'
    restore restore-admin 'f=/backups/sync/'$run'/$ADMIN_DB_NAME.sql.gz
      gunzip -t "$f" && gunzip -c "$f" | mariadb -h "$TOKENSERVER_DB_HOST" -u"$ADMIN_DB_USER" -p"$ADMIN_DB_PASSWORD" "$ADMIN_DB_NAME"'
    # only when no device has the data any more
    restore restore-storage 'f=/backups/sync/'$run'/$STORAGE_DB_NAME.sql.gz
      gunzip -t "$f" && gunzip -c "$f" | mariadb -h "$STORAGE_DB_HOST" -u"$STORAGE_DB_USER" -p"$STORAGE_DB_PASSWORD" "$STORAGE_DB_NAME"'
    kubectl scale deploy/$F-syncstorage --replicas=1
    ```

    PostgreSQL: the Sync server's role first (the `sync-role` init container of the Sync server, alone), then the one Sync database as that role; the Sync server's init container then creates the admin UI's database and roles, and its dump goes in after it:

    ```bash
    kubectl get deploy $F-syncstorage -o json | jq '{apiVersion: "v1", kind: "Pod", metadata: {name: "ffs-sync-role"},
      spec: {restartPolicy: "Never", containers: [.spec.template.spec.initContainers[] | select(.name == "sync-role")]}}' | kubectl apply -f -
    kubectl wait --for=jsonpath='{.status.phase}'=Succeeded pod/ffs-sync-role --timeout=5m && kubectl delete pod ffs-sync-role
    restore restore-sync 'f=/backups/sync/'$run'/$TOKENSERVER_DB_NAME.sql.gz
      gunzip -t "$f" && gunzip -c "$f" |
        PGPASSWORD="$TOKENSERVER_DB_PASSWORD" psql -h "$TOKENSERVER_DB_HOST" -U "$TOKENSERVER_DB_USER" -d "$TOKENSERVER_DB_NAME" -v ON_ERROR_STOP=1'
    kubectl scale deploy/$F-syncstorage --replicas=1
    kubectl wait --for=condition=Ready pod -l app.kubernetes.io/instance=ffs,app.kubernetes.io/component=syncstorage --timeout=10m
    restore restore-admin 'f=/backups/sync/'$run'/$ADMIN_DB_NAME.sql.gz
      gunzip -t "$f" && gunzip -c "$f" |
        PGPASSWORD="$ADMIN_DB_PASSWORD" psql -h "$TOKENSERVER_DB_HOST" -U "$ADMIN_DB_USER" -d "$ADMIN_DB_NAME" -v ON_ERROR_STOP=1'
    ```

1. The admin UI again, `kubectl scale deploy/$F-admin --replicas=1`, and remove what the restore left: `kubectl delete job restore-tokenserver restore-admin restore-storage restore-sync --ignore-not-found`. The migrations bring an older schema up to date. A later `helm upgrade` keeps the replicas of the chart (one each).

## Upgrades

```bash
helm upgrade ffs oci://ghcr.io/porelli/firefox-sync/charts/firefox-sync --version <new version> \
  -f my-values.yaml --wait --timeout 10m
```

(or `--reuse-values` instead of `-f`, as the admin UI's commands do: the values of the last install or upgrade, with the `--set` given). The Sync server stops, then starts again with its migrations and init container first (`strategy: Recreate`): a minute without Sync, which Firefox retries. The generated secrets are read back; never change `SYNC_MASTER_SECRET` or `METRICS_HASH_SECRET` in your `existingSecret` (every Firefox would have to sign in again), nor a database password the server already has.

- **The images.** `image.syncstorageTag`, `image.initTag` and `image.adminTag` follow `latest`, published here only after the tests passed ([SYNC.md](SYNC.md#upgrades)). With `image.pullPolicy: IfNotPresent` (the default) a node that has `latest` does not pull a newer one: pin the tags and change them on upgrade, or set `image.pullPolicy: Always` and `kubectl rollout restart deploy/ffs-firefox-sync-syncstorage` (the admin UI: `deploy/ffs-firefox-sync-admin`) to take the newest.
- **The database images** (`database.image.<backend>`). `mariadb:lts` upgrades its data at the first start on a new release (`MARIADB_AUTO_UPGRADE`), with no way back but a backup. `postgres:18` pins the major: the official image keeps its data at `/var/lib/postgresql/<major>/docker` and refuses to start on an older major's, so a newer major needs a dump and restore ([Restoring](#restoring)) or `pg_upgrade` ([DATABASES.md](DATABASES.md#another-postgresql-major)). With your own server, `database.image.<backend>` is only the backups' client: `pg_dump` must be at least the server's major.
- **existingSecret**: a key a new chart version needs (its release notes say so; `ADMIN_DB_PASSWORD` and `POSTGRES_SYNC_PASSWORD` came during the pre-releases of 0.1.0) goes into it before the upgrade, or the pods wait in `CreateContainerConfigError`. The chart's own Secret gets it by itself.

`helm uninstall ffs` removes the pods and Services and keeps the data: the Secret, the backups' PVC and the databases' PVCs (`data-ffs-firefox-sync-*`, Kubernetes never deletes a StatefulSet's). A new install with the same release name finds them. To remove it all for good: `kubectl delete secret,pvc -l app.kubernetes.io/instance=ffs`.

## Limits

- **One Sync server.** `syncstorage.replicas` stays 1: the migrations and the `maxUsers` init run in its init containers, and two at once is not tested.
- **No self-hosted accounts yet**: [FXA.md](FXA.md) with docker compose or the Quadlets.
- **Release names.** The names the admin UI builds from the release (the Services, the StatefulSets, the Sync server's Deployment, the backup CronJob) are never truncated: one over Kubernetes' limits is refused at render time, with the name that is too long. (Only the one-shot Job that binds the backups' PVC has a shortened name of its own.) With the default fullname `<release>-firefox-sync`, the release name is at most 24 characters with the bundled MariaDB or MySQL (`<fullname>-tokenserver-db`, a StatefulSet: 52), 30 with the bundled PostgreSQL (`<fullname>-postgres`), 32 with the backups (`<fullname>-backup`, a CronJob: 52): the shortest of those that apply. A release name that contains `firefox-sync` is the fullname itself; `fullnameOverride` sets it.
- **Probes.** The database servers have up to 30 minutes for their first start (a new database, a long recovery) and are restarted only after 5 minutes without an answer: a server that recovers is not killed half-way. The Sync server is ready once its heartbeat answers, as the healthcheck of compose.

## Troubleshooting

- The Sync server's pod stays in `Init:` (`Init:Error`, `Init:CrashLoopBackOff`): the logs of its init containers, in their order: `kubectl logs deploy/ffs-firefox-sync-syncstorage -c wait-db` (the database servers answer), `-c sync-role` (PostgreSQL), `-c migrate` (a refused password stops it here), `-c db-init` (`maxUsers`). A database server: `kubectl logs sts/ffs-firefox-sync-tokenserver-db` and `sts/ffs-firefox-sync-storage-db` (MariaDB, MySQL), `sts/ffs-firefox-sync-postgres` (PostgreSQL).
- `CreateContainerConfigError`: a key missing from your `existingSecret`, see [existingSecret](#existingsecret).
- `helm install` fails with `firefox-sync: ...` before anything starts: the values are refused (a release name too long, `database.bundled=false` without `database.external.host` or `existingSecret`, the admin UI's Ingress on the Sync server's host...). The message says what to set.
- `413 Request Entity Too Large` in `about:sync-log`: the body size of the Ingress, see [Ingress](#ingress).
- The bundled MySQL in `CrashLoopBackOff` on kind or k3s, on an Ubuntu host with `mysql-server` installed: the host's AppArmor profile for `/usr/sbin/mysqld` also confines the `mysqld` of the `mysql:8.4` image, in pods that run unconfined. It denies `/etc/my.cnf`, `/usr/share/mysql-8.4` and the init file of the admin UI's users: the first start aborts half-way and every next one finds no `mysql.user`. Disable that profile (the host's own MySQL then runs unconfined too), then delete the PVC of the half-made database:

    ```bash
    sudo ln -s /etc/apparmor.d/usr.sbin.mysqld /etc/apparmor.d/disable/ && sudo apparmor_parser -R /etc/apparmor.d/usr.sbin.mysqld
    ```

    or use MariaDB (the default) or PostgreSQL. Docker's containers are not affected (they run in `docker-default`).

## Tests

`tests/helm.sh` checks the chart: `lint` (its renders, the checks of the values, the NOTES), `parity` (the same env, commands and probes as compose) and `e2e <mariadb|mysql|postgres>` on a kind cluster: `helm install` and `helm upgrade` as here, a backup with `kubectl create job --from=cronjob/...`, and its dumps restored with the commands of [ADMIN.md#restoring](ADMIN.md#restoring) in pods of the backup's spec, into empty database servers like the chart's (not the steps of [Restoring](#restoring) as a whole). Those steps, as written here, were run by hand on kind for MariaDB and PostgreSQL, not in CI. See [TESTING.md](TESTING.md#the-helm-chart).
