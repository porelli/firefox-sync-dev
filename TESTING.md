# Tests

Every image build runs the tests in [tests/](/tests) before the multi-arch tags (e.g. `syncstorage-rs-mysql-latest`) are published:
- [`tests/e2e.sh`](/tests/e2e.sh) `<mysql|postgres>`: starts the docker compose stack (for `mysql` on MariaDB, with `SYNC_DB=mysql` on MySQL 8.4) and checks start-up order, SYNC_MAX_USERS, domain changes, a Firefox-like sign-in and sync through the tokenserver ([`test_client_flow.py`](/tests/test_client_flow.py), using upstream's mock FxA server) and runs upstream's storage and tokenserver integration tests, after an upgrade from an install before `ADMIN_DB_PASSWORD` (with `UPGRADE_FROM=<checkout>` that release's own files and images) that moves the admin UI's event log out of the Sync server's users' reach ([DATABASES.md](DATABASES.md#the-admin-uis-own-database)). With `EXTERNAL_DB=1` the same on a database server outside the stack ([DATABASES.md](DATABASES.md)) with only the documented grants: MySQL 8.4 with binary logging, or PostgreSQL 18 set up by a role that is no superuser, with an owner that is no superuser. `tests/e2e-fxa.sh` and `tests/podman.sh` take it too: one MySQL 8.4, or MariaDB (`FXA_MARIADB_IMAGE`) with `FXA_DB=mariadb`, for Sync and the accounts, MariaDB with binary logging for the Quadlets; `EXTERNAL_DB=fxa` puts only the accounts there, with one user for the accounts and the sign-up policy. The builds of the Sync images run `EXTERNAL_DB=1 tests/e2e.sh` on both backends and `SYNC_DB=mysql tests/e2e.sh mysql`, those of the admin UI that and `EXTERNAL_DB=1 tests/e2e-fxa.sh` (MySQL, amd64); the other combinations run locally only
- [`tests/podman.sh`](/tests/podman.sh): rootless Podman, with Quadlets (also with self-hosted accounts) and with `docker compose` on the Podman socket, configured with `prepare_environment.sh`. It also checks the MySQL Quadlets as rendered, and with `SYNC_DB=mysql` it runs the compose and Quadlet phases on MySQL 8.4
- [`tests/e2e-fxa.sh`](/tests/e2e-fxa.sh): the stack with self-hosted Mozilla accounts behind an HTTPS proxy and a mail catcher: the setup with `prepare_environment.sh`, sign-up, OAuth and sync like Firefox does ([`test_fxa_flow.py`](/tests/test_fxa_flow.py)), the sign-up policy and the admin UI ([`test_fxa_admin.py`](/tests/test_fxa_admin.py)), a real Firefox signing up on one profile and syncing to a second one ([`test_fxa_browser.py`](/tests/test_fxa_browser.py)) and the pairing server. It runs with the newest Mozilla accounts release every week, and on amd64 and arm64 for the [accounts images](/.github/workflows/fxa.yml). With `FXA_DB=mariadb` the accounts database is MariaDB instead of MySQL 8.4, `FXA_MARIADB_IMAGE` (default `mariadb:12.3`; the accounts images run it on `mariadb:12.3`, `mariadb:11.8` and, as the canary of the next major, `mariadb:lts`; `tests/podman.sh` takes `FXA_DB` too, for the Quadlets)

The three end with every container that keeps running healthy and the one-shot ones exited with 0 ([`tests/healthy.sh`](/tests/healthy.sh)); `tests/podman.sh` also checks that each Quadlet that keeps running has the healthcheck of its compose service (the same command and timings), and that no such service lacks one.

All can be run locally against any published tag, e.g. `TAG=latest tests/e2e.sh mysql`.

[`tests/fxa-upgrade.sh`](/tests/fxa-upgrade.sh) upgrades the self-hosted accounts in place from an older release (`FXA_FROM`) with the steps of [FXA.md](FXA.md#upgrades), and checks that sessions, devices, refresh tokens and Sync data survive the migrations; the accounts images run it from the published release before publishing a new one.

Not run by the image builds, locally only: [`tests/migrate.sh`](/tests/migrate.sh) `<scenario>`, the database moves of [MIGRATING.md](MIGRATING.md) from other Sync servers (Mozilla's compose files, dan-r, jeena, NixOS, YunoHost) and the upgrades of older firefox-sync releases, run with the commands of the guide as written there and checked with a client of upstream's mock FxA ([`migrate_client.py`](/tests/migrate_client.py)).

## The Helm chart

[`tests/helm.sh`](/tests/helm.sh), for the [Helm chart](HELM.md) (needs `helm`, `jq` and PyYAML; `lint` and `parity` also `docker compose`, for its config only, as `lint` runs `parity`; `e2e` also `kind`, `kubectl` and docker, which builds the init and admin images and hands the syncstorage image to the cluster with `docker save`):
- `lint`: `helm lint` with each values file of [charts/firefox-sync/ci/](/charts/firefox-sync/ci), then checks of the renders: every long-running container has its probes, `maxUsers` and the values the schema refuses, the database images, the Secret (generated, read back, `helm.sh/resource-policy: keep`, the admin UI's optional secrets authoritative from the values, `existingSecret`), the names over Kubernetes' limits refused, your own database server and its checks, the Ingresses (the admin UI's never on the Sync server's host), the backups' CronJob, the NOTES; then `parity`.
- `parity [case...]`: [`tests/helm_parity.py`](/tests/helm_parity.py), the chart against compose: per compose service and chart container the same variables and values (the hosts and secrets aside), the same commands, probes with the timings of compose's healthchecks, the copied scripts byte-identical, for each backend, with the admin UI and the backups on and off.
- `e2e <mariadb|mysql|postgres>`: the chart on a throwaway kind cluster (`ffs-helm-<backend>`, deleted at the end), with the init and admin images built from the tree (`SKIP_BUILD=1`: the published ones of `REPOSITORY` and `TAG`), upstream's mock FxA and a Firefox-like client ([`test_client_flow.py`](/tests/test_client_flow.py)): `helm install --wait`, the client flow, the database users' grants, `maxUsers` refused by the schema, a wrong database password stopping the pod in its init containers (no ready endpoint), `helm upgrade` keeping every secret, the admin UI on and off ([ADMIN.md](ADMIN.md#tests)), a backup with `kubectl create job --from=cronjob/...` restored into empty database servers as [ADMIN.md#restoring](ADMIN.md#restoring) says. `EXTERNAL_DB=1` (mysql, postgres): on a database server of its own in the cluster, which the chart does not manage (`database.bundled=false`, `existingSecret`, the Ingresses with a class no controller serves), as `tests/e2e.sh`'s `EXTERNAL_DB=1`. With MySQL on an Ubuntu host with `mysql-server`, it stops first while the host's AppArmor profile for `mysqld` is loaded, and prints the commands that disable it ([HELM.md](HELM.md#troubleshooting)).

[`.github/workflows/helm.yml`](/.github/workflows/helm.yml) runs `ct lint`, kubeconform with each `ci/` values file, `tests/helm.sh lint`, and `e2e` on MariaDB, MySQL and PostgreSQL, and on your own MySQL and PostgreSQL server, on every push that changes the chart, its tests, the compose files, `db/`, the backups or the admin UI, and every week. On a tag `chart-v<version>` (the version of `Chart.yaml`), after all of them passed, it publishes the chart to `oci://ghcr.io/<owner>/<repository>/charts/firefox-sync` (for this repository `oci://ghcr.io/porelli/firefox-sync/charts/firefox-sync`), with `Chart.yaml`'s annotation `org.firefox-sync/chart` set to that address (the admin UI's `helm upgrade` commands show it). A stable version only from a commit of the default branch; a pre-release (`0.1.0-dev.1`) from any branch, to test the publishing (`helm install` without `--version` or `--devel` never picks one). A version is published once, never replaced: a tag of a version already there fails. A new package starts private on GitHub: the maintainer makes it public once, in the package's settings.

## Upstream patches

The images are built from Mozilla's releases, plus the upstream pull requests of [upstream-patches.yml](/upstream-patches.yml) that this project needs before they are released (its header has the details). In both workflows the job that picks the release runs [`tests/test_upstream_patches.py`](/tests/test_upstream_patches.py) (the decisions of [`.github/scripts/upstream-patches.py`](/.github/scripts/upstream-patches.py) on fixtures, no network: `python3 tests/test_upstream_patches.py`) and lists what is to apply; each build applies it to the checked out release, for every architecture, and the image gets the list in its label `org.firefox-sync.upstream-patches` and the summary of the run. The tests then run on those images. Tests that work around an upstream bug read the label: `tests/e2e.sh` skips upstream's `test_node_assignment.py::test_user_creation` on MariaDB only for images without [mozilla-services/syncstorage-rs#2638](https://github.com/mozilla-services/syncstorage-rs/pull/2638).

- Adding a pull request: review it, then an entry with its head repository, the full sha of the reviewed head commit and of its merge base (`base`; the commands are in the header of upstream-patches.yml), why, and what to undo once it is released (`when_released`). Exactly `base...sha` is applied: a pull request that moves, is rebased or retargeted changes nothing until the entry does. On a branch the images are built and tested, not published; merged into main, the change rebuilds the current release of the component with it, under the same tags (a new digest): fxa.yml rebuilds when the published image was built for another plan (its label `org.firefox-sync.upstream-patches-plan`), syncstorage-rs.yml has the patches in the key of the images it reuses. A manual run on main does the same. In fxa.yml upstream's code runs in build jobs without write access, which hand an OCI archive to push jobs; these push it under tags of the run (`fxa-mono-<release>-linux-<arch>-run<id>`, the same for the pairing server), the tests use those digests, and main publishes the multi-arch tags from them. syncstorage-rs.yml writes the tags main reuses (keys, per-architecture tags, build cache) from main only, a branch gets key tags of its own. Both run one at a time per branch.
- The outcomes, in the run: applied (open, or merged after the release built): the build goes on, with a notice if the pull request has commits after the pinned sha, which are not applied until the sha is moved. Merged and in the release (or its changes already in the sources): not applied, and the job `upstream-patches`, after publishing, fails with the entry and its `when_released`. Closed without merging, another head repository, a sha not in the pull request's history, changes that don't apply to the release, or merged and released but its changes not in the sources: the build fails and nothing is published.
- Removing an entry: in one commit with what its `when_released` says.

Locally, against the real pull requests (read-only, `gh` signed in): `python3 .github/scripts/upstream-patches.py plan fxa-mono v1.347.3`, or `apply <component> <tag> <checkout>` on a clone of the release.
